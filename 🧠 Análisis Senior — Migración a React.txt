════════════════════════════════════════════════════════

   ── Los 6 puntos críticos que van a morder si no se planean ──

   🔴 1. Estado global disperso en localStorage/sessionStorage

      El proyecto tiene estado esparcido en mínimo 6 claves
      distintas sin gestión centralizada:

         localStorage: parkingPrices
         localStorage: parkingSchedule
         localStorage: registeredUsers
         localStorage: notificationSettings
         localStorage: puntoParkUser     ← sesión de usuario
         sessionStorage: adminAuth        ← sesión de admin

      En React → una sola fuente de verdad con Zustand + persist
      middleware (zustand/middleware). Context API sin cuidado
      causa re-renders en cascada.

   🔴 2. Chart.js con instancias globales (window._chart)

      En panel.js:
         window._chartIngresos = new Chart(...)
         window._chartOcupacion = new Chart(...)

      En React esto explota porque el DOM se desmonta y remonta.
      El canvas queda "en uso" y lanza error:

         "Canvas is already in use"

      Solución: useRef para el canvas + useEffect con cleanup
      obligatorio. El hook useDestroyChart debe llamar chart.destroy()
      en la función de retorno del useEffect.

   🔴 3. 40+ inline event handlers mezclados con HTML

      Patrón actual:
         onclick="navigate('dashboard')"
         onsubmit="handleLogin(event)"
         oninput="updatePricePreview()"

      En React → props de evento + useCallback. Si no se
      memoizan, cada render recrea las funciones y causes
      re-renders innecesarios en componentes hijos.

   🔴 4. Guard de auth en top-level del módulo

      En panel.js líneas 3-6:
         if (!isDev && sessionStorage.getItem('adminAuth') !== 'true') {
             window.location.href = '../Admi.html';
         }

      Esto NO funciona en React porque:
      - Corre antes de que el árbol de componentes exista
      - No puede usar React Router (useNavigate)
      - Da falsos positivos si el contexto de auth no está listo

      Solución: authStore (Zustand) + ProtectedRoute component con
      useNavigate(), no con window.location.

   🔴 5. Chart.js destroy/reinit pattern frágil

      Patrón actual:
         function _destroyChart(id) {
             const chart = Chart.getChart(id);
             if (chart) chart.destroy();
         }

      Llamado en múltiples lugares sin garantía de orden.
      En React el patrón correcto es:
         useEffect(() => {
             const chart = new Chart(ctx, config);
             return () => chart.destroy();
         }, [dependencies]);

   🔴 6. jsPDF + xlsx cargados por CDN

      En el HTML actual:
         <script src="...jspdf.umd.min.js"></script>

      Y en panel.js:
         if (typeof window.jspdf === 'undefined') { ... }

      En Vite esto NO funciona porque:
      - No hay window.jspdf en un bundle empaquetado
      - jsPDF y xlsx deben instalarse como npm packages
      - Hay que importarlos como módulos ES

   ── Problemas adicionales ──

   🟡 CSS global sin aislamiento
      Styles.css (1,738) + panel.css (3,068) + pantalla-usuario.css
      (1,796) = ~6,600 líneas de CSS global. Sin encapsulación.

   🟡 Rutas relativas frágiles con espacios
      Ej: '../Login/Pantalla%20Usuario/PantallaUsuario.html'
      Dan 404 en producción. React Router usa /dashboard, /admin.

   🟡 Sin TypeScript
      Errores solo en runtime. TypeScript los detecta al compilar.

                        │ WebSockets        │
                        └────────┬─────────┘
                                 │
            ┌────────────────────┼────────────────────┐

   │ PostgreSQL      │  │ Módulo Visión  │  │ Módulo Analítica│

   Regla de oro:
   - Node.js maneja TODO lo del negocio: auth, usuarios, vehículos,
     reservas, precios, WebSockets en tiempo real
   - Python SOLO entra para los módulos de IA (visión + analítica)
   - Comunicación Node.js ↔ Python vía HTTP interno
   - Node.js NUNCA toca un frame de video, solo recibe JSON
     procesado por Python + OpenCV

   ⚡ Lo que Node.js da fácil:
   ├── Auth con JWT (control total, conocido)
   ├── WebSockets con socket.io (badge "En vivo" del panel)
   ├── Misma sintaxis frontend y backend (valor educativo)
   └── npm unificado con monorepo

   ¿Por qué NO Next.js todavía?
   El proyecto es 100% client-side con localStorage. Next.js trae
   SSR/SSG que choca con localStorage en el servidor (errores de
   hidratación). Primero React + Vite, estabilizar, después evaluar
   Next.js para el landing público.

 7. PATRONES CRÍTICOS PARA CHART.JS EN REACT
════════════════════════════════════════════════════════

   ⚠️ Este es el punto que más errores causa en la migración.

   ── MAL (patrón actual en panel.js) ──

   window._chartIngresos = new Chart(...)
   // sin cleanup, sin useRef, global scope


   ── BIEN (patrón React) ──

   const chartRef = useRef<HTMLCanvasElement>(null)
   const chartInstance = useRef<Chart | null>(null)

   useEffect(() => {
       const ctx = chartRef.current?.getContext('2d')
       if (!ctx) return

       chartInstance.current = new Chart(ctx, { ... })

       return () => {
           chartInstance.current?.destroy()
           chartInstance.current = null
       }
   }, [data]) // ← dependencies controlan recreación

   return <canvas ref={chartRef} />


   ── MEJOR (con react-chartjs-2) ──

   import { Doughnut } from 'react-chartjs-2'

   function LiveOccupancy() {
       const data = { /* ... */ }
       const options = { /* ... */ }

       return <Doughnut data={data} options={options} />
   }

   // react-chartjs-2 maneja el lifecycle automáticamente
   // pero hay que registrar los componentes globalmente:
   import { Chart, ArcElement, Tooltip, Legend } from 'chart.js'
   Chart.register(ArcElement, Tooltip, Legend)

════════════════════════════════════════════════════════
 9. RED FLAGS — ERRORES A EVITAR
════════════════════════════════════════════════════════

   🚩 NO migrar todo de golpe
      Hacerlo página por página. La app vanilla sigue funcionando
      mientras migras (strangler fig). No paralizar el proyecto.

   🚩 NO mantener ambos paneles en el mismo bundle
      Admin y usuario son experiencias distintas. Usar lazy loading
      con React.lazy(() => import('./pages/Admin/AdminPage')) + Suspense.

   🚩 NO usar Redux
      Zustand es suficiente y mucho más simple para este proyecto.

   🚩 NO mezclar CSS vainilla con Tailwind
      Cuando migres una página, migra TAMBIÉN su CSS. No dejar
      archivos .css sueltos conviviendo con Tailwind.

   🚩 NO escribir componentes sin TypeScript primero
      Las interfaces deben definirse ANTES de cualquier componente.
      Esto evita retrabajo y errores de tipo.

   🚩 NO mantener auth fragmentado
      Unificar en authStore (Zustand) desde el día 1. No repetir el patrón
      de 3 sistemas de almacenamiento diferentes.

   🚩 NO usar Tailwind v4
      V4 tiene breaking changes activos y documentación incompleta.
      Usar v3.4 para esta migración.

   🚩 NO dejar jsPDF + xlsx en CDN
      Importarlos como npm packages. window.jspdf NO existe en Vite.

   🚩 NO poner el guard de auth en top-level
      El AuthGuard debe ser un componente dentro del árbol de React,
      NO código suelto que corre antes del mount.

   🚩 NO olvidar el cleanup de Chart.js
      Cada chart creado en useEffect debe tener su destroy()
      en la función de retorno. Memory leaks garantizados.

 11. CONCLUSIÓN
════════════════════════════════════════════════════════

   El proyecto actual es funcional pero con deuda técnica típica
   de un MVP en vanilla (auth fragmentada, charts sin cleanup,
   CDN, CSS global, rutas con espacios).

   La migración a React + TypeScript + Tailwind + Zustand no solo
   resuelve los problemas de producción sino que prepara el código
   para la integración con Flux AI (backend Node.js, WebSockets,
   módulos Python independientes).

   La estrategia es Strangler Fig:
   1. React se construye AL LADO del vanilla, no lo reemplaza de golpe
   2. Login + Registro primero (establecen infraestructura de auth)
   3. Páginas públicas después
   4. Dashboard usuario
   5. Dashboard admin al final (con charts y lógica compleja)
   6. Service layer desacoplado para cuando llegue el backend

   Stack final confirmado:
   ├── React 18 + Vite + TypeScript
   ├── Zustand (estado global + persist)
   ├── Tailwind v3.4
   ├── React Router v6
   ├── Chart.js + react-chartjs-2 (con cleanup)
   ├── jsPDF + xlsx (npm, no CDN)
   └── Node.js + Express (backend futuro)
